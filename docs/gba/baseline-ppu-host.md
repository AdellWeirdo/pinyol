# Host baseline of the real `ppu_render`

Measured 2026-10-19 on the development Mac (Apple M5 Pro, arm64, macOS 26.5.2), with the real `src/ppu.c`
(`ppu_render`), not the simplified kernel in `firmware/main/bench.c`. This is step 0 of `05-perf-esp32s3.md`
(section 3.1 and 3.2), done on the host.

**Read this first: host timings are NOT ESP32-S3 cycles.** A 240x160 frame that the board needs milliseconds for
takes 0.1-0.2 ms here (M-series core: wide, fast caches, no flash cache, no PSRAM). Only rankings and ratios
between scenes can carry over to the board, and even those depend on the compiler (xtensa GCC 14.2 on the board) and on
the S3's cache and memory placement, which the host does not model. Use the host numbers (a) as a pixel-exact
regression gate through the hashes, and (b) as a hint to which feature is expensive per unit.

Everything lives outside the repo, in the scratchpad. Nothing in `np2d` was changed except this file.

## 1. What was measured

`harness.c` calls the real `ppu_render` on a 240x160 RGB565 frame. `hal_parallel` is defined as in
`platform/null`: part 0 then part 1, serially on one thread (as on the board in `bench_run`, before the second
core's task exists). Scenes are the table of `bench.c`; content copies `bench.c`'s `make_content` (same LCG, seed
12345, same stripes-with-holes tiles, same 32 disc sprites, same Mode 7 perspective table, same per-frame motion),
converted to what `ppu.c` wants: 8 bpp index tiles (1024 tiles x 64 bytes), 64x64-tile maps with hflip/vflip/bank
bits, 16x16 indexed sprites (all priority 0, as `bench.c` draws them on top), affine map 64x64 with 256 tiles and
the per-line table in `PPU.line.affine`. `ppu_tile_rows` fills `rows`, as the engine does.

Differences from `bench.c`, all forced by `ppu.c`:

- **"Max" is affine + 3 tile layers + 128 sprites**, not 4 + affine: the PPU has four backgrounds (`PPU_BGS`). The
  affine layer is BG3 (priority 3); regular layers are BG0.. with priority = index.
- "Clear only" runs the full `line()` path with every background off and no sprites (not the `ppu_blank` shortcut).
- Tile and sprite pixels go through the palette (`bg_pal`/`obj_pal`, RGB565) as in the engine, not into an index frame.

Effect scenes (the two requested, plus decomposition extras marked `x:`):

| Scene | Setup |
|---|---|
| FX: 4L+alpha+window | 4 tile layers, `FX_ALPHA` first target BG0, second BG1-3+backdrop, eva 10 / evb 6; window 0 = x 40-200, y 20-140 (all layers + FX), window 1 = x 100-140, all lines (BG0, BG2, FX), outside = BG1-3 + OBJ (no FX) |
| FX: 128 spr half OBJ_BLEND | 128 sprites, odd ones `OBJ_BLEND`, eva 8 / evb 8, second target all BGs + backdrop; no background layers (the blend sees the backdrop) |
| x: 4L+alpha only / x: 4L+window only | the above without the window / without the alpha |
| x: 4L+128 spr half OBJ_BLEND | same blend over 4 layers |
| x: 128 sprites off-screen | 128 sprites parked at y = -100: only the per-line visit and y-reject cost |

Method: for each scene, 50 warm-up frames, then 2000 timed frames (each frame has the scroll, sprite and Mode 7
state of `bench.c`'s `render_task`, set up outside the timed region). One `ppu_render` call is timed with
`clock_gettime_nsec_np(CLOCK_UPTIME_RAW)` (41.7 ns ticks). Median and p95 are over the 2000 frames. Every number
below is the **median of 3 complete runs** (the 3 runs of one build differ by 1-3% in the medians; the raw spread is
in `summarize.py` output). Hash: FNV-1a 64 over the bytes of the frame buffer (little-endian RGB565), chained over
frames 0-119 of the scene (frames numbered from the first measured frame).

## 4. Relative cost between scenes

All numbers: clang -O2, content A. The right-hand columns repeat the `docs/measurements.md` kernel cycles of
`bench.c` (4.0 M cycles = a 60 fps core) as shares of GBA mode 0, to check whether the simplified bench ranks the
scenes like the real renderer.

| Scene | real ppu_render (host) | share of GBA mode 0 | bench.c kernel (ESP32-S3) | share of GBA mode 0 |
|---|---|---|---|---|
| clear only | 4.3 us | 3% | 25 k cyc | 1% |
| 1 layer | 28.3 us | 20% | 471 k cyc | 23% |
| 4 layers | 104.0 us | 72% | 1561 k cyc | 75% |
| 128 sprites 16x16 | 41.0 us | 29% | 538 k cyc | 26% |
| 1 affine layer | 38.6 us | 27% | 801 k cyc | 39% |
| light: 2L+32 spr | 62.2 us | 43% | 966 k cyc | 47% |
| GBA mode 0: 4L+128 spr | 143.6 us | 100% | 2074 k cyc | 100% |
| Mode 7: aff+1L+64 spr | 83.9 us | 58% | 1507 k cyc | 73% |
| Max: aff+3L+128 spr | 151.7 us | 106% | n/a | n/a |
| FX: 4L+alpha+window | 171.8 us | 120% | n/a | n/a |
| FX: 128 spr half OBJ_BLEND | 69.2 us | 48% | n/a | n/a |

The real renderer ranks the scenes like the bench kernel to within ten percentage points, except the affine layer
(real 27% of mode 0, kernel 39%) and Mode 7 (58% vs 73%): `bg_affine_x`'s power-of-two path (shifts, no multiplies,
no per-pixel bank) is cheaper relative to a tile layer than `bench.c`'s affine kernel was. Sprites and tile layers
are within a few points. So the board's `bench.c` table is a usable proxy for the tile/sprite mix, and
pessimistic for affine.

Per unit of work, net of the clear-only cost (one frame = 38,400 pixels). Rows marked "pass" are whole-frame costs
that a scene pays once:

| Feature | us/frame | ns per frame pixel | note |
|---|---|---|---|
| tile layer (avg of 4) | 24.9 | 0.65 | per layer, 38,400 px |
| tile layer (1 layer scene) | 24.0 | 0.62 | per layer |
| affine layer (Mode 7 table) | 34.3 | 0.89 | per layer |
| sprite 16x16 on screen (128 spr, drawn+visited) | 0.3 | 0.01 | per sprite |
| sprite visit/reject only (off-screen) | 14.5 | 0.38 | all 128; 20,480 visits |
| alpha blend pass (4L: alpha only - 4 layers) | 69.7 | 1.82 | whole frame |
| 2 windows (4L: window only - 4 layers) | 15.1 | 0.39 | whole frame |
| OBJ_BLEND on 64 of 128 sprites (no BG) | 28.2 | 0.73 | whole frame |
| OBJ_BLEND on 64 of 128 sprites (over 4 layers) | 34.8 | 0.91 | whole frame |

Ranking, most expensive per unit first:

1. **Alpha blending (FX_ALPHA over 4 layers): +70 us, 1.8 ns per frame pixel**, 2.8x the cost of a tile layer.
   Two parts: the final pass stops being a straight copy (0.8 us) and becomes the per-pixel blend loop (56-63 us across runs), and
   every layer pays the extra `under` store (tile layers 98 -> 114 us). On this host content the blend is applied to
   every pixel of BG0 (first target).
2. **OBJ_BLEND sprites**: one blended sprite anywhere in the frame forces the full final pass and `track` for the
   whole frame: +28 us over plain sprites with no background (final pass 0.8 -> 28.5 us), +35 us over 4 layers.
   The cost is per frame, not per blended sprite.
3. **Affine layer**: 34 us, 0.89 ns/pixel, about 1.4x a tile layer (24-25 us, 0.65 ns/pixel).
4. **Tile layer**: about 25 us each; four layers are 72% of GBA mode 0.
5. **Sprites**: 128 sprites cost 37 us in total, of which **14.5 us is visiting 20,480 (sprite, line) pairs that are
   rejected by the y test** (the "off-screen" scene; the sprite list is walked on every line). Drawing is the other
   22 us. A sprite costs 0.29 us on average; a scene's sprite cost has a fixed per-sprite floor (0.11 us here) whether
   it is on screen or not.
6. **Windows**: +15 us over 4 layers (0.39 ns/pixel): `windows()` itself is 1.2 us; the rest is the `win` copy of the layer
   loops (a `show[]` test per pixel, and no opaque-run shortcut).
7. Backdrop fill and straight copy-out: 0.7 us and 0.8 us per frame. Negligible. Clear only is 4.3 us in total, of which
   about 2 us is per-line dispatch (the 4 priorities x 4 backgrounds checks), not pixels.

## 5. Determinism and hashes

All 15 scenes are deterministic: fixed LCG seed, no time or thread dependence (`hal_parallel` is serial). The hash
is over frames 0-119 of each scene, so it does not depend on how many frames are timed. Verified:

- two runs of the same binary give identical hashes;
- the hashes are identical across clang/gcc-16 and -O2 / -O3 / -O3 -funroll-loops (6 builds), and identical in the
  two profiling builds (`ppu_prof.c`), for both content sets A and B. So the compiler optimisation level does not
  change a single output pixel here, and the instrumented copy's logic is unchanged.
- "clear only" and "x: 128 sprites off-screen" share the hash `684ff1e0e683e325` (nothing is drawn), a sanity check.
- Content B differs from A only in tile-layer scenes (T3 lists B's hashes); sprite, affine and clear scenes have the same
  hash in both.

To detect a later pixel change: re-run `run_all.sh` (or one binary: `out/bench_clang_O2 150 A`, content `A`) and compare the `hash=`
fields with the T1 table (content A) and T3 (content B). Hash of a frame buffer depends on endianness: valid on arm64 and x86_64
(both little-endian) but not on a big-endian host.

**Attribution** (clang -O2 unless noted):

- *Backdrop clear*: 0.65 us (gcc-16: 2.2 us), under 1% of any scene except "clear only". Not a target.
- *Tile layers*: 24-26 us per layer. Dominant in every scene that has them (GBA mode 0: 101 of 143 us; 4 layers: 98 of 104).
- *Affine layer*: 34 us, flat across scenes (the per-line table is the same).
- *Sprites*: 37-39 us for 128 sprites (52 us on gcc-16); 11 us for 32; 20.7 us for 64. About 14.7 us is the per-line visit
  of the 128-entry list (off-screen scene: 14.7 us).
- *Blend / compose (final pass)*: 0.8 us when no effect applies; 28.6 us with `OBJ_BLEND` sprites over a plain background; 35 us in
  4L+alpha+window; 56-63 us for 4L+alpha alone (more than with the window, which hides FX on part of the frame).
  Alpha also raises the tile-layer time by 10-15 us via `under` stores (4 layers 98 -> 114 us).
- *Windows*: `windows()` is 1.1-1.3 us; the window cost is mostly inside the layer loops (4 layers 98 -> 117 us).
- *Bitmap layers*: not exercised (counter exists, always 0).

Everything is `always_inline`, so the profile is only per variant: GBA mode 0 spends 3368 of 3413 samples (98.7%) in
`layers_plain`, 34 in `render_part` (the final copy, backdrop) and 11 in `ppu_render`; Mode 7: 3323 of 3414 (97.3%) in
`layers_plain`; 4L+alpha+window: 2614 in `layers_win_track` (76.7%) and 789 in `render_part` (23.1%), against the
counters' 22.5% for the final pass plus windows and backdrop, which agree. `sample` cannot split inside the inlined
loops, which is why the counters were needed. `xctrace` was not used.

## 7. Not done, and limits

- **Not ESP32-S3 time.** No cycles, no cache behaviour (64 KB data cache, tiles/maps in PSRAM, IRAM placement), no dual-core
  split (`hal_parallel` is serial here; the board gets 1.6-1.9x from two cores).
- **Compiler**: Apple clang and Homebrew gcc-16 (arm64), not xtensa-esp-elf GCC 14.2. IDF's `-fno-builtin-memset`,
  `-fno-jump-tables`, `-mlongcalls` and the `ppu_inside` linker scheme are not reproduced. clang ignores the
  `no-tree-loop-distribute-patterns` pragma (it does not make the memmove calls that GCC does).
- **Scenes not covered** (`05-perf-esp32s3.md` 3.1 lists them): `rows == NULL`, scroll_x % 8 variants, PSRAM-placed tile data,
  bitmap layers, RGB565 sprites, affine sprites, mosaic, fades (`FX_LIGHTEN`/`FX_DARKEN`), per-line `fx_ev`, object window, 8
  sprites of 64x64, sprites with mixed priorities, core scaling. Only the nine `bench.c` scenes and the two effect scenes (plus
  four extras) were run.
- **Content is synthetic** (`bench.c`'s). The real Lua games (section 3.3 of the digest) were not run on the host.
- "Max" is affine + 3 layers (not 4 + affine).
- The call to `ppu_render` is timed alone; between frames the harness hashes and sets state, which can evict some cache
  (on a core with large caches this has little effect).
- `sample` could not split inlined code; `xctrace` was not tried.
- Timer resolution 41.7 ns; the counters' per-call quantisation averages out over the 160 lines but is visible in the
  "other" column.

## The renderer's changes of 2026-10-20, measured again against the one before them

`ppu_golden_test --bench [scene [frames]]` times a frame of each golden scene (best of five runs). Release build on a Mac, best of five
interleaved rounds (a single run moves by up to 10 %), each against `src/ppu.c` at `9354805`, before `line_pal`, the turned-sprite span and
the blend's tracking:

| Scene | big (all of them specialised) | now |
|---|---|---|
| layers4 | +0.3 % | -3.2 % |
| mode0 | -1.7 % | -1.9 % |
| fx.alpha-window | -3.0 % | -2.4 % |

- **The turned sprite's span is the one real gain**: 16 turned 64 x 64 sprites 607 -> 67 us a frame with the double area, 204 -> 64 without.
- **The blend's tracking gained nothing against the original**: the -11.7 % first written for it was measured against the renderer after

- **The code size is what changed the most, and it is the console's RAM**: `ppu.c` runs from IRAM, which the ESP32-S3 shares with data.

  line-palette builds are two (no window and no blend, the sky-and-sea case; and one for the rest, chosen as it runs), and only tile
  layers have two tracking builds: 31.3 KB, the same frames, the same gains.
- **Tried and left out: the three channels blended at once** (exact to the bit when the weights add up to 16 or less: 375 million cases
  compared): mixed on the computer.
